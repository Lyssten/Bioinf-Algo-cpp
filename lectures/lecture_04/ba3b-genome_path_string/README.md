# Genome Path String (BA3B)

## Задача

Восстановить строку по её геномному пути (последовательности перекрывающихся k-меров).

**Вход:** последовательность k-меров `Pattern₁, ..., Patternₙ`, где последние k−1 символов `Patternᵢ` совпадают с первыми k−1 символами `Patternᵢ₊₁`
**Выход:** строка `Text` длины k+n−1, составленная из данных k-меров

Формат входного файла Rosalind:
```text
kmer1
kmer2
...
kmern
```

**Пример:**
```
Вход:
ACCGA
CCGAA
CGAAG
GAAGC
AAGCT

Вывод: ACCGAAGCT
```

## Теория

### Геномный путь

Строка `Text` длины n может быть разбита на последовательность перекрывающихся k-меров:
```
Text = s₁s₂...sₙ
Pattern₁ = s₁s₂...sₖ
Pattern₂ = s₂s₃...sₖ₊₁
...
Patternₙ₋ₖ₊₁ = sₙ₋ₖ₊₁...sₙ
```

Эта последовательность называется **геномным путём** (Genome Path). По сути, это k-мерная композиция из BA3A, но **с сохранённым порядком**.

### Ключевое свойство перекрытий

Соседние k-меры перекрываются на (k − 1) символов:
```
ACCGA
 CCGAA
  CGAAG
   GAAGC
    AAGCT
─────────
ACCGAAGCT
```

Каждый следующий k-мер добавляет ровно **один новый символ** — свой последний. Длина результата = k + (n − 1), где n — количество k-меров.

Формально: `Suffix(Patternᵢ) = Prefix(Patternᵢ₊₁)`, где суффикс и префикс имеют длину k − 1.

## Применение

### В биологии

- **Сборка после выравнивания на референс.** Когда риды картированы (выровнены) на известный референсный геном, они образуют упорядоченную цепочку перекрывающихся фрагментов — в точности геномный путь. Программа **SAMtools consensus** выполняет именно эту операцию: склеивает выровненные риды в одну строку. Например, при ресеквенировании штамма *E. coli* K-12 100× покрытием Illumina, SAMtools восстанавливает полный геном (4.6 Мб) из ~30 миллионов упорядоченных ридов.

- **Длинные чтения (long reads).** Секвенаторы Oxford Nanopore (MinION) и PacBio (Sequel II) генерируют риды длиной 10–100 Кб, которые покрывают геном с нахлёстом. Если риды правильно упорядочены, восстановление генома — тривиальная операция склейки. Ассемблер **minimap2 + miniasm** сначала выстраивает риды в цепочку, затем склеивает перекрытия — по сути, решает задачу BA3B.

- **Scaffold gap filling.** При сборке генома остаются «дыры» (gaps) между контигами. Программа **GapFiller** находит риды, перекрывающие границы контигов, выстраивает их в цепочку и склеивает — снова геномный путь.

### В других областях

- **TCP/IP.** Пакеты данных в сети приходят в произвольном порядке, но каждый имеет порядковый номер (sequence number). TCP-стек ядра ОС переупорядочивает их и склеивает в непрерывный поток — та же операция склейки перекрывающихся фрагментов. При скачивании файла в 1 Гб через 10-гигабитное соединение ядро Linux обрабатывает ~700 000 пакетов по 1500 байт.

- **Потоковое аудио/видео.** Аудиокодеки (Opus, Vorbis) используют перекрывающиеся фреймы (overlap-add): каждый фрейм на 50% перекрывается с предыдущим. Декодер склеивает фреймы, плавно восстанавливая сигнал. Принцип идентичен: перекрытие → взять начало первого фрейма + новую часть каждого следующего.

- **Восстановление документов.** Криминалисты восстанавливают порезанные шредером документы: если полоски уже правильно упорядочены по перекрытию текста на краях, результат — простая склейка. Система **unshredder** использует OCR + алгоритм склейки перекрытий.

## Алгоритм

### Идея

Задача тривиальна, если порядок фрагментов известен: берём первый k-мер целиком, а от каждого следующего — только последний символ (всё остальное уже есть из предыдущих перекрытий). Вся сложность реальной сборки — не в склейке, а в **определении правильного порядка** фрагментов. Именно для этого в следующих задачах строятся графы.

### Псевдокод
```
GenomePathString(Patterns):
    Text ← Patterns[0]
    for i ← 1 to |Patterns| - 1:
        Text ← Text + последний символ Patterns[i]
    return Text
```

## Реализация на C++

```cpp
std::string solve(const InputData& data) {
    std::string result = data.kmers[0];             // (1)
    for (size_t i = 1; i < data.kmers.size(); ++i) {
        result += data.kmers[i].back();             // (2)
    }
    return result;                                   // (3)
}
```

## Разбор кода

**1. Инициализация первым k-мером**
```cpp
std::string result = data.kmers[0];
```
- Копируем первый k-мер целиком — это основа результата. Создаётся **копия** строки (не ссылка), так как `result` будет дальше модифицироваться.
- `data.kmers[0]` — доступ к первому элементу вектора за O(1). Не проверяет границы (в отличие от `.at(0)`).
- Зачем копировать, а не начать с пустой строки? Альтернатива `result = ""; for (all) result += kmers[i].back();` не работает: у первого k-мера нужно взять все k символов, а не один.

**2. `std::string::back()` и `operator+=`**
```cpp
result += data.kmers[i].back();
```
- `back()` — возвращает ссылку (`char&`) на последний символ строки за O(1). Эквивалентно `str[str.size() - 1]`, но читаемее и не требует знания длины.
- `operator+=(char)` — добавляет один символ в конец строки. Амортизированная стоимость O(1): `std::string` удваивает внутренний буфер при нехватке места (аналогично `vector`).
- Почему именно `back()`, а не `substr`? Ключевое свойство перекрытия: каждый новый k-мер добавляет **ровно один** символ. Брать подстроку длиной 1 через `substr` — аллокация + копия, а `back()` — просто чтение одного байта.

**3. Возврат строки (move semantics)**
```cpp
return result;
```
- Компилятор применяет NRVO (Named Return Value Optimization): строка конструируется прямо в вызывающем коде, без копирования.
- Даже без NRVO: move-конструктор `std::string` перемещает внутренний буфер (указатель + размер + capacity) за O(1), а не копирует символы.

**4. Валидация перекрытий**
```cpp
for (size_t i = 0; i + 1 < data.kmers.size(); ++i) {
    std::string suffix = data.kmers[i].substr(1);
    std::string prefix = data.kmers[i + 1].substr(0, k - 1);
    if (suffix != prefix)
        throw std::invalid_argument(...);
}
```
- `substr(1)` — подстрока с позиции 1 до конца: суффикс длины k−1.
- `substr(0, k-1)` — первые k−1 символов: префикс.
- `i + 1 < size()` вместо `i < size() - 1` — защита от переполнения `size_t`, если вектор пустой.
- Валидация не влияет на основную логику, но помогает отловить некорректный вход до получения бессмысленного результата.

## Анализ сложности

### Время: O(n · k)

**Обоснование.** Алгоритм состоит из двух частей:
1. Основной цикл: n−1 итераций, каждая — O(1) (чтение `back()` + дозапись одного символа).
2. Валидация: n−1 сравнений подстрок длины k−1 → O(n·k).

Без валидации — **O(n)**, с валидацией — **O(n·k)**.

**Узкое место в коде (с валидацией):**
```cpp
std::string suffix = data.kmers[i].substr(1);          // O(k) — создание подстроки
std::string prefix = data.kmers[i + 1].substr(0, k-1); // O(k) — создание подстроки
if (suffix != prefix) ...                                // O(k) — посимвольное сравнение
```
На каждой итерации: два `substr` (аллокация + копирование k−1 символов) и одно сравнение. Итого O(k) на итерацию × (n−1) итераций = O(n·k).

**Основной цикл (если бы не валидация):**
```cpp
result += data.kmers[i].back();  // O(1) амортизированно
```
Добавление одного символа — O(1), итого O(n). Это делает основную логику **линейной по числу k-меров**.

### Память: O(n + k)

**Обоснование.** Результат — строка длины k + n − 1, что O(n + k).

**Основные структуры данных:**
```cpp
std::string result = data.kmers[0];  // строка длины k, растёт до k + n - 1
```
Входные данные (n строк по k символов) занимают O(n·k), но это входной буфер, а не дополнительная память алгоритма. Собственная память алгоритма — только строка `result`.
