# De Bruijn Graph of k-mers (BA3E)

## Задача

Построить граф де Брёйна по заданной коллекции k-меров.

**Вход:** коллекция k-меров (по одному на строку)
**Выход:** список смежности графа де Брёйна (отсортированный по узлам)

Каждый k-мер становится ребром из своего префикса (первые k−1 символов) в суффикс (последние k−1 символов). Дубликаты k-меров порождают дубликаты рёбер.

Формат входного файла Rosalind:
```text
kmer1
kmer2
...
```

**Пример:**
```
Вход:
GAGG
CAGG
GGGG
GGGA
CAGG
AGGG
GGAG

Выход:
AGG -> GGG
CAG -> AGG,AGG
GAG -> AGG
GGA -> GAG
GGG -> GGA,GGG
```

## Теория

### От строки к коллекции k-меров

В задаче BA3D мы строили граф де Брёйна из строки — извлекали k-меры сами. Но в реальности секвенатор выдаёт **только набор k-меров** (ридов), а исходная строка (геном) неизвестна. Именно это моделирует текущая задача: на входе — «россыпь» k-меров без привязки к позиции в геноме.

### Построение графа

Граф де Брёйна `DeBruijn(Patterns)` по коллекции k-меров:
- **Узлы** — все уникальные (k−1)-меры, встречающиеся как префиксы или суффиксы входных k-меров
- **Рёбра** — каждый k-мер → направленное ребро `Prefix(kmer) → Suffix(kmer)`

```
Prefix(GAGG) = GAG,   Suffix(GAGG) = AGG   →  GAG → AGG
Prefix(CAGG) = CAG,   Suffix(CAGG) = AGG   →  CAG → AGG
Prefix(CAGG) = CAG,   Suffix(CAGG) = AGG   →  CAG → AGG  (дубликат!)
```

### Мультирёбра и глубина покрытия

Ключевое отличие от BA3D: входная коллекция может содержать **дубликаты k-меров**, и каждый дубликат порождает отдельное ребро. Результат — **мультиграф** (граф с параллельными рёбрами).

В примере `CAGG` встречается дважды → из `CAG` в `AGG` идут два параллельных ребра. Это не ошибка — в реальном секвенировании каждый участок генома прочитывается многократно (глубина покрытия 30×–100×). Мультирёбра отражают эту кратность.

Мультирёбра помогают отличить **настоящие повторы** в геноме от **ошибок секвенирования**: настоящий повтор виден во многих ридах (высокая кратность), ошибка — в одном-двух.

## Применение

### В биологии

- **Рабочая модель реального ассемблера.** Эта задача — точная модель того, что делает первый шаг ассемблера SPAdes: получает миллионы k-меров из Illumina-ридов и строит из них граф де Брёйна. Для генома *E. coli* (4.6 Мб, 100× покрытие) SPAdes обрабатывает ~460 миллионов k-меров при k = 55. Уникальных (k−1)-меров (узлов графа) — около 9 миллионов, рёбер — ~460 миллионов.

- **Повторы в геноме — главная проблема сборки.** Мультирёбра показывают повторы: если k-мер встречается 3 раза в разных ридах, это может означать, что соответствующий участок ДНК повторяется 3 раза в геноме. Геном человека на ~45% состоит из повторов (Alu-элементы ~300 нт, LINE-1 ~6 Кб, сегментарные дупликации до 200 Кб). Повторы создают неоднозначность: эйлеров путь в графе с мультирёбрами **неединственный**, поэтому ассемблер разбивает граф на контиги — однозначные фрагменты.

- **Контроль качества секвенирования.** Программа **FastQC** строит распределение k-меров и ищет аномалии. Неожиданно частые k-меры — признак адаптерного загрязнения (артефакт библиотеки). Например, k-мер `AGATCGGAAGAGC` (начало адаптера Illumina) не должен встречаться 10 000 раз в ридах бактерии.

### В других областях

- **Дедупликация данных в хранилищах.** Системы вроде ZFS и Btrfs разбивают файлы на блоки фиксированной длины и хранят граф зависимостей. Мультирёбра показывают дублированные блоки, которые можно хранить один раз. Для хранилища виртуальных машин дедупликация экономит до 80% пространства.

- **Анализ сетевого трафика.** Системы обнаружения вторжений (Snort, Suricata) разбивают сетевые пакеты на n-граммы байтов. Граф де Брёйна n-грамм нормального трафика отличается от трафика при DDoS-атаке: атака порождает большое число одинаковых мультирёбер (повторяющиеся пакеты).

- **Рекомендательные системы.** Последовательности действий пользователей (просмотр → клик → добавление в корзину) образуют k-граммы. Граф де Брёйна показывает типичные «маршруты» и их частоту. Amazon использует подобные графы поведения для предсказания следующего действия пользователя.

## Алгоритм

### Идея

Алгоритм идентичен BA3D, но вместо извлечения k-меров из строки мы получаем их напрямую. Для каждого k-мера: отрезаем первый символ → суффикс (целевой узел), отрезаем последний → префикс (исходный узел). Добавляем ребро. `map` автоматически склеивает одинаковые узлы. После построения графа сортируем списки смежности — Rosalind ожидает отсортированный вывод.

### Псевдокод
```
DeBruijnFromKmers(Patterns):
    graph ← пустой словарь (узел → список целей)
    for each kmer in Patterns:
        prefix ← kmer[0..k-2]
        suffix ← kmer[1..k-1]
        graph[prefix].append(suffix)
    отсортировать списки целей каждого узла
    return graph
```

## Реализация на C++

```cpp
AdjList solve(const InputData& input) {
    AdjList graph;                                             // (1)

    for (const auto& kmer : input.kmers) {                     // (2)
        std::string prefix = kmer.substr(0, kmer.size() - 1);  // (3)
        std::string suffix = kmer.substr(1);                    // (4)
        graph[prefix].push_back(suffix);                        // (5)
    }

    for (auto& [node, targets] : graph) {                      // (6)
        std::sort(targets.begin(), targets.end());
    }

    return graph;
}
```

## Разбор кода

**1. `AdjList` — тот же тип, что и в BA3D**
```cpp
using AdjList = std::map<std::string, std::vector<std::string>>;
AdjList graph;
```
- `map` гарантирует лексикографический порядок узлов при итерации.
- Пустой `map` — размер 0, без предварительных аллокаций.
- Структура идентична BA3D: мы строим тот же граф, но из другого входа.

**2. Range-based for с `const auto&`**
```cpp
for (const auto& kmer : input.kmers) {
```
- `auto` выводит тип `const std::string&` (ссылка на константную строку).
- Без `&` на каждой итерации создавалась бы копия строки — бесполезная работа.
- Отличие от BA3D: там цикл `for (size_t i = 0; ...)` по позициям в строке, здесь — по элементам вектора.

**3. `kmer.size() - 1` — безопасно при непустых строках**
```cpp
std::string prefix = kmer.substr(0, kmer.size() - 1);
```
- `kmer.size() - 1` при пустой строке переполнит `size_t` (станет ~2⁶⁴). Но `validateInput()` гарантирует длину ≥ 2.
- Для k-мера длины k: `substr(0, k-1)` = первые k−1 символов = префикс.

**4. `substr(1)` без второго аргумента — до конца строки**
```cpp
std::string suffix = kmer.substr(1);
```
- `substr(pos)` — подстрока от `pos` до конца. Для k-мера длины k: k−1 символов, начиная со второго.

**5. Мультирёбра — автоматически**
```cpp
graph[prefix].push_back(suffix);
```
- Если `CAGG` встречается дважды, `graph["CAG"]` получит два `push_back("AGG")`. Вектор хранит оба — это и есть мультирёбра.
- `operator[]` в `map`: O(k · log m) на поиск/вставку (m — число узлов).

**6. Сортировка списков смежности**
```cpp
for (auto& [node, targets] : graph) {
    std::sort(targets.begin(), targets.end());
}
```
- `auto&` (без `const`) — нужна мутабельная ссылка для `std::sort`.
- `[node, targets]` — structured bindings (C++17): `node = const std::string&`, `targets = std::vector<std::string>&`.
- `std::sort` — introsort, O(d · k · log d) для каждого узла, где d = degree (число рёбер из узла).
- Зачем сортировать? Rosalind ожидает `CAG -> AGG,AGG`, а не `CAG -> AGG,AGG` в произвольном порядке. Для мультирёбер порядок может отличаться от порядка во входных данных.

## Анализ сложности

### Время: O(n · k · log n), где n — число k-меров

**Обоснование.** Алгоритм состоит из двух фаз:
1. Построение графа: n k-меров, каждый → два `substr` за O(k) + вставка в `map` за O(k · log m).
2. Сортировка списков смежности: суммарно O(n · k · log n) в худшем случае (все рёбра из одного узла).

**Узкое место в коде:**
```cpp
graph[prefix].push_back(suffix);         // O(k · log m) — поиск в map
// ...
std::sort(targets.begin(), targets.end()); // O(d · k · log d) — сортировка
```
Обе операции содержат O(k) на сравнение строк. Для первой фазы: n × O(k · log m) = O(n · k · log m). Для второй: суммарно O(n · k · log D_max), где D_max — максимальная степень узла.

С `unordered_map` вместо `map` первая фаза ускорилась бы до O(n · k), но пришлось бы сортировать ключи отдельно.

### Память: O(n · k)

**Обоснование.** Граф хранит n рёбер, каждое — два (k−1)-мера.

**Основные структуры данных:**
```cpp
AdjList graph;  // m уникальных узлов + n суффиксов в векторах
```
- Узлов: m ≤ 2n (каждый k-мер даёт максимум 2 новых (k−1)-мера).
- Каждый узел — строка длины k−1 + указатель на вектор.
- Каждое ребро — строка длины k−1 в векторе.
- Итого: O(n · k) на строки + O(m) overhead от `map`.
