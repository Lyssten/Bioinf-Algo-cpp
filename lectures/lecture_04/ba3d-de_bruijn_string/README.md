# De Bruijn Graph of a String (BA3D)

## Задача

Построить граф де Брёйна строки Text для заданного k.

**Вход:** целое число `k` и строка `Text`
**Выход:** граф де Брёйна DeBruijn_k(Text) в виде списка смежности

Формат входного файла Rosalind:
```text
k
Text
```

**Пример:**
```
k: 4
Text: AAGATTCTCTAC
Вывод:
AAG -> AGA
AGA -> GAT
ATT -> TTC
CTA -> TAC
CTC -> TCT
GAT -> ATT
TCT -> CTA,CTC
TTC -> TCT
```

## Теория

### От overlap-графа к графу де Брёйна

В задаче BA3C граф перекрытий имел **вершины = k-меры**, а сборка генома = гамильтонов путь (NP-полная задача). Николаас де Брёйн (1946) предложил элегантную альтернативу: поменять ролями вершины и рёбра.

| | Overlap-граф (BA3C) | Граф де Брёйна (BA3D) |
|---|---|---|
| **Вершины** | k-меры | (k−1)-меры |
| **Рёбра** | перекрытие суффикс=префикс | k-меры |
| **Сборка =** | Гамильтонов путь (**NP-полная**) | Эйлеров путь (**линейное время**) |
| **Число вершин** | n (число k-меров) | ≤ 4^(k-1) (уникальные (k−1)-меры) |

Ключевая идея: каждый k-мер `AAGA` — это не вершина, а **ребро** из `AAG` в `AGA`. Одинаковые (k−1)-меры, встречающиеся в разных позициях, **склеиваются** в одну вершину. Теперь сборка генома — это обход всех рёбер ровно по разу (эйлеров путь), а не всех вершин (гамильтонов путь).

### Построение графа де Брёйна строки

DeBruijn_k(Text) строится в три шага:
1. Извлекаем все k-меры из строки Text (как в BA3A)
2. Каждый k-мер → **ребро**: из его **префикса** (первые k−1 символов) в его **суффикс** (последние k−1 символов)
3. Одинаковые узлы **склеиваются** (gluing)

Пример для Text = `AAGATTCTCTAC`, k = 4:
```
k-мер    Префикс → Суффикс    (ребро)
─────    ───────────────────
AAGA     AAG → AGA
AGAT     AGA → GAT
GATT     GAT → ATT
ATTC     ATT → TTC
TTCT     TTC → TCT
TCTC     TCT → CTC            ← узел TCT уже существует
CTCT     CTC → TCT            ← склейка: CTC и TCT повторно используются
TCTA     TCT → CTA
CTAC     CTA → TAC
```

Узел `TCT` встречается трижды (как суффикс `TTCT`, как префикс `TCTC` и `TCTA`), но в графе он **один** — с двумя исходящими рёбрами (→ CTC и → CTA). Склейка — это то, что делает граф де Брёйна компактнее overlap-графа.

### Почему эйлеров путь, а не гамильтонов?

В overlap-графе BA3C каждый k-мер — вершина, и мы должны пройти через каждую вершину ровно раз (гамильтонов путь). В графе де Брёйна каждый k-мер — ребро, и мы должны пройти через каждое ребро ровно раз (эйлеров путь). Разница принципиальна:
- Гамильтонов путь — NP-полный, нет эффективного алгоритма
- Эйлеров путь — решается за O(|E|) алгоритмом Хирхольцера (BA3F)

Эта смена перспективы — одна из красивейших идей в компьютерной биологии.

## Применение

### В биологии

- **Современные ассемблеры коротких чтений.** Практически все ассемблеры для Illumina-данных строят граф де Брёйна из строки (или из набора ридов). **SPAdes** (2012, Санкт-Петербургский университет) — самый популярный ассемблер для бактериальных геномов: строит серию графов де Брёйна при разных k (21, 33, 55, 77...) и объединяет результаты. **Velvet** (2008) — исторически первый ассемблер на графе де Брёйна. **MEGAHIT** (2015) — ассемблер для метагеномики (смесь ДНК сотен организмов).

- **Коррекция ошибок секвенирования.** Программа **BFC** (Bloom Filter Corrector, Heng Li, 2015) строит граф де Брёйна из ридов и использует его для коррекции ошибок: если k-мер встречается 1 раз (ошибка), но отличается на 1 нуклеотид от k-мера с покрытием 50× (правильный), он заменяется. Для генома человека (3.2 Гб, 30× покрытие ≈ 100 Гб ридов) BFC исправляет ~1% всех нуклеотидов.

- **Вариантный анализ (variant calling).** **Cortex** строит граф де Брёйна из ридов нескольких индивидов одновременно. «Пузыри» (bubbles) в графе — места, где геномы различаются — это SNP и инделы. Метод позволяет обнаруживать мутации без референсного генома.

### В других областях

- **Последовательности де Брёйна.** Эйлеров цикл в графе де Брёйна порядка n над алфавитом из σ символов даёт кратчайшую циклическую строку, содержащую все подстроки длины n. Длина = σⁿ. Пример: строка `0011` содержит все двоичные 2-граммы: `00`, `01`, `11`, `10`. Применение: **взлом кодовых замков** — минимальное число нажатий для перебора всех k-значных PIN-кодов. Для 4-значного PIN (σ=10, n=4) нужна последовательность из 10⁴ = 10 000 цифр вместо 4 × 10 000 = 40 000 при наивном переборе.

- **Тестирование цифровых схем.** Последовательность де Брёйна подаётся на вход регистра сдвига (LFSR) для проверки всех возможных n-битных состояний за минимальное число тактов. Intel и AMD используют подобные последовательности при верификации процессоров.

- **Фокусы с картами.** Фокусник раскладывает 32 карты в ряд (красные и чёрные). Зритель указывает на любые 5 подряд. Фокусник, видя только цвета, называет позицию — это работает, потому что карты выложены в порядке последовательности де Брёйна B(2, 5): все 32 двоичных 5-граммы уникальны.

## Алгоритм

### Идея

Для каждого k-мера в строке: отрезаем первый символ → получаем суффикс (целевая вершина), отрезаем последний символ → получаем префикс (исходная вершина). Добавляем ребро из префикса в суффикс. Если вершина с таким именем уже существует — используем её (склейка). `std::map` автоматически выполняет склейку: все обращения к `graph["TCT"]` попадают в один и тот же вектор.

### Псевдокод
```
DeBruijnGraph(Text, k):
    graph ← пустой словарь (node → list of targets)
    for i from 0 to |Text| - k:
        kmer ← Text[i..i+k-1]
        prefix ← kmer[0..k-2]
        suffix ← kmer[1..k-1]
        graph[prefix].append(suffix)
    return graph
```

## Реализация на C++

```cpp
using AdjList = std::map<std::string, std::vector<std::string>>;

AdjList solve(const InputData& input) {
    AdjList graph;                                                     // (1)

    for (size_t i = 0; i + input.k <= input.text.size(); ++i) {       // (2)
        std::string kmer = input.text.substr(i, input.k);              // (3)
        std::string prefix = kmer.substr(0, input.k - 1);             // (4)
        std::string suffix = kmer.substr(1, input.k - 1);             // (5)
        graph[prefix].push_back(suffix);                               // (6)
    }

    return graph;
}
```

## Разбор кода

**1. `using AdjList` — псевдоним типа**
```cpp
using AdjList = std::map<std::string, std::vector<std::string>>;
```
- `using` (C++11) создаёт псевдоним для длинного типа. Аналог `typedef`, но читаемее для шаблонов.
- `std::map` — красно-чёрное дерево, хранит ключи отсортированными. Выбран для автоматической лексикографической сортировки узлов в выводе.
- Ключ — имя узла ((k−1)-мер), значение — вектор целевых узлов (список смежности).

**2. Безопасная граница цикла**
```cpp
for (size_t i = 0; i + input.k <= input.text.size(); ++i) {
```
- `i + k <= size` вместо `i <= size - k`: при `size < k` вычитание переполнит `size_t` (обернётся в ~2⁶⁴), а сложение безопасно.
- Количество итераций: n − k + 1, где n = |Text|.

**3. Извлечение k-мера**
```cpp
std::string kmer = input.text.substr(i, input.k);
```
- `substr(pos, len)` — новая строка длины `len` с позиции `pos`. Аллокация в куче при k > 15 (SSO).
- Можно обойтись без промежуточной строки: `prefix = text.substr(i, k-1)`, `suffix = text.substr(i+1, k-1)`. Но отдельный k-мер улучшает читаемость.

**4–5. Префикс и суффикс k-мера**
```cpp
std::string prefix = kmer.substr(0, input.k - 1);  // первые k-1 символов
std::string suffix = kmer.substr(1, input.k - 1);  // последние k-1 символов
```
- Префикс = k-мер без последнего символа: `AAGA` → `AAG`.
- Суффикс = k-мер без первого символа: `AAGA` → `AGA`.
- Каждый вызов `substr` — аллокация + копирование k−1 символов.

**6. Добавление ребра — автоматическая «склейка»**
```cpp
graph[prefix].push_back(suffix);
```
- `operator[]` в `map`: если ключ `prefix` не существует — создаёт запись с пустым `vector<string>`.
- `push_back` добавляет `suffix` в список смежности.
- **Склейка** происходит автоматически: если `prefix = "TCT"` уже есть в `map`, новый суффикс добавляется к существующему вектору. Не нужно явно проверять уникальность узлов.
- Порядок суффиксов в списке соответствует порядку их появления в строке.

**7. Structured bindings при форматировании**
```cpp
for (const auto& [node, targets] : graph) {
```
- C++17 structured bindings: `[node, targets]` распаковывает `std::pair<const std::string, std::vector<std::string>>`.
- `const auto&` — без копирования пары. Итерация по `map` гарантирует порядок по ключу.

## Анализ сложности

### Время: O(m · k · log m), где m = n − k + 1

**Обоснование.** Для каждого из m k-меров:
1. Три `substr` — суммарно O(k) на аллокацию и копирование.
2. Вставка в `map` — O(k · log m): поиск позиции в дереве за O(log m) сравнений, каждое сравнение строк — O(k).

Итого: m × (k + k · log m) = **O(m · k · log m)**.

**Узкое место в коде:**
```cpp
graph[prefix].push_back(suffix);  // O(k · log m) — поиск в map
```
Именно `operator[]` у `map` — bottleneck: на каждом обращении красно-чёрное дерево выполняет O(log m) сравнений ключей, каждое сравнение строк длины k−1 — O(k). С `unordered_map` было бы O(k) амортизированно (хэширование строки), но вывод не был бы отсортирован.

### Память: O(m · k)

**Обоснование.** Граф хранит до m рёбер, каждое ребро — две строки длины k−1.

**Основные структуры данных:**
```cpp
AdjList graph;  // до m записей в map, каждая — ключ O(k) + вектор суффиксов
```
- Количество уникальных узлов ≤ 2m (не более двух новых (k−1)-меров на каждый k-мер).
- `map` — ~40 байт overhead на каждый узел дерева (указатели, цвет, балансировка).
- Для *E. coli* (n = 4.6 Мб, k = 55): m ≈ 4.6M рёбер, ~4.6M × 54 × 2 ≈ 500 Мб на строки + overhead = существенно. На практике ассемблеры используют компактные представления (compressed de Bruijn graph).
