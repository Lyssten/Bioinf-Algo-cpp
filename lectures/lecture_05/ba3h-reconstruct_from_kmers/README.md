# Reconstruct a String from its k-mer Composition (BA3H)

## Задача

Восстановить строку по её k-мер композиции.

**Вход:** целое число `k` и коллекция k-меров
**Выход:** строка Text, k-мер композиция которой совпадает с входной коллекцией

Формат входного файла Rosalind:
```text
4
CTTA
ACCA
TACC
GGCT
GCTT
TTAC
```

**Пример:**
```
Вход:
k = 4
k-меры: CTTA ACCA TACC GGCT GCTT TTAC

Вывод: GGCTTACCA
```

## Теория

### Полный конвейер сборки генома

Эта задача объединяет все предыдущие задачи лекции в один конвейер --- **полный цикл сборки генома** из ридов:

```
k-меры (BA3A)  →  граф де Брёйна (BA3E)  →  эйлеров путь (BA3G)  →  строка (BA3B)
```

1. **Вход:** коллекция k-меров --- «нарезанный» геном, как его выдаёт секвенатор
2. **Граф де Брёйна (BA3E):** каждый k-мер = ребро из префикса в суффикс. Одинаковые (k-1)-меры склеиваются в одну вершину
3. **Эйлеров путь (BA3G):** проходим по каждому ребру ровно раз, восстанавливая порядок k-меров
4. **Spell (BA3B):** первый узел пути + последний символ каждого следующего узла = исходная строка

### Почему конвейер работает?

Ключевое наблюдение: если строка Text имеет k-мер композицию `{GGCT, GCTT, CTTA, TTAC, TACC, ACCA}`, то граф де Брёйна этих k-меров гарантированно имеет эйлеров путь (при условии, что композиция порождена одной строкой). Каждый k-мер --- ребро, и порядок обхода рёбер в эйлеровом пути воспроизводит порядок k-меров в строке.

### Единственность решения

Эйлеров путь может быть **неединственным**, если в графе есть циклические альтернативы. Для данной задачи Rosalind гарантирует единственность. В реальной сборке неединственность --- главная проблема: повторы в геноме создают «развилки», и ассемблер вынужден разбивать граф на контиги (однозначные участки).

### Пример: пошаговая сборка

```
k-меры: GGCT, GCTT, CTTA, TTAC, TACC, ACCA

Граф де Брёйна (каждый 4-мер → ребро из 3-мер-префикса в 3-мер-суффикс):
  GGC → GCT    (ребро GGCT)
  GCT → CTT    (ребро GCTT)
  CTT → TTA    (ребро CTTA)
  TTA → TAC    (ребро TTAC)
  TAC → ACC    (ребро TACC)
  ACC → CCA    (ребро ACCA)

Эйлеров путь: GGC → GCT → CTT → TTA → TAC → ACC → CCA

Spell: GGC + T + A + C + C + A = GGCTTACCA
```

## Применение

### В биологии

- **Сборка бактериальных геномов из коротких чтений.** Это именно то, что делают современные ассемблеры. **SPAdes** (2012, Algorithmic Biology Lab, СПбГУ) собирает геном *E. coli* (4.6 Мб) из ~5 миллионов Illumina-ридов длиной 150 нт: строит серию графов де Брёйна при k = 21, 33, 55, 77, 99, 127, находит в каждом эйлеровы пути и объединяет результаты. Итог: ~100 контигов, N50 ~200 Кб, покрывающих 99.9% генома. Весь процесс занимает ~10 минут на ноутбуке.

- **Метагеномная сборка.** Программа **MEGAHIT** (2015, Университет Гонконга) собирает геномы сотен организмов одновременно из одного образца (например, микробиом кишечника). Для образца с ~50 миллионами ридов MEGAHIT строит компактный граф де Брёйна и находит набор эйлеровых путей --- каждый путь соответствует фрагменту генома одного из организмов. Из одного образца кишечника можно восстановить ~500 бактериальных геномов.

- **Сборка геномов вирусов.** Геном SARS-CoV-2 (~30 Кб) собирается из ампликонных ридов. При k = 31 граф де Брёйна имеет ~30 000 узлов и ~30 000 рёбер. Эйлеров путь восстанавливает полный геном за миллисекунды. Программа **Unicycler** (2017) использует этот подход для сборки вирусных геномов и малых плазмид. За время пандемии было собрано >16 миллионов геномов SARS-CoV-2 --- каждый прошёл через этот конвейер.

### В других областях

- **Восстановление текста из фрагментов.** Документ разрезан на перекрывающиеся полоски (k-граммы символов). Задача --- восстановить оригинал. Это в точности BA3H с алфавитом из букв вместо нуклеотидов. Криминалисты восстанавливают измельчённые документы по этому принципу. Проект DARPA Shredder Challenge (2011) --- восстановление 5 документов из 10 000 фрагментов --- был решён подобным подходом.

- **Реконструкция последовательности событий.** Лог-файл разбит на перекрывающиеся «окна» длины k. Восстановление полной последовательности событий --- задача BA3H. Системы анализа логов (Splunk, ELK) используют аналогичные методы для восстановления порядка событий при частичной потере логов.

- **Сборка фрагментированных файлов (file carving).** При восстановлении данных с повреждённого диска forensic-инструменты находят перекрывающиеся блоки данных и собирают из них файлы. Программа **Scalpel** строит граф зависимостей блоков и ищет пути --- аналог эйлерова пути в графе де Брёйна.

## Алгоритм

### Идея

Задача декомпозируется на три уже решённые подзадачи:

1. **buildDeBruijn (BA3E):** для каждого k-мера создаём ребро `prefix -> suffix`. Одинаковые (k-1)-меры автоматически склеиваются благодаря `map`.
2. **eulerianPath (BA3G):** находим startNode и endNode по дисбалансу степеней, добавляем временное ребро, запускаем Хирхольцера, разрезаем цикл.
3. **spellString (BA3B):** берём первый узел пути целиком, затем от каждого следующего узла --- только последний символ.

Вся логика сборки --- три строки кода. Сложность в каждой подфункции, но композиция элегантна.

### Псевдокод
```
ReconstructFromKmers(kmers):
    // Шаг 1: граф де Брёйна
    graph ← пустой словарь
    for each kmer in kmers:
        graph[kmer[0..k-2]].append(kmer[1..k-1])

    // Шаг 2: эйлеров путь
    path ← EulerianPath(graph)    // BA3G

    // Шаг 3: восстановление строки
    result ← path[0]
    for i from 1 to |path| - 1:
        result += path[i].back()
    return result
```

## Реализация на C++

```cpp
using Graph = std::map<std::string, std::vector<std::string>>;

Graph buildDeBruijn(const std::vector<std::string>& kmers) {       // (1)
    Graph graph;
    for (const auto& kmer : kmers) {
        std::string prefix = kmer.substr(0, kmer.size() - 1);      // (2)
        std::string suffix = kmer.substr(1);                        // (3)
        graph[prefix].push_back(suffix);                            // (4)
    }
    return graph;
}

std::vector<std::string> eulerianPath(Graph& graph) {              // (5)
    std::map<std::string, int> inDeg, outDeg;
    std::set<std::string> allNodes;

    for (auto& [v, neighbors] : graph) {
        allNodes.insert(v);
        outDeg[v] = static_cast<int>(neighbors.size());
        for (auto& u : neighbors) {
            inDeg[u]++;
            allNodes.insert(u);
        }
    }

    std::string startNode, endNode;                                 // (6)
    for (auto& v : allNodes) {
        int diff = outDeg[v] - inDeg[v];
        if (diff == 1) startNode = v;
        else if (diff == -1) endNode = v;
    }

    if (startNode.empty()) {                                        // (7)
        return eulerianCycle(graph, graph.begin()->first);
    }

    graph[endNode].push_back(startNode);
    auto cycle = eulerianCycle(graph, startNode);
    graph[endNode].pop_back();

    for (size_t i = 0; i + 1 < cycle.size(); ++i) {                // (8)
        if (cycle[i] == endNode && cycle[i + 1] == startNode) {
            std::vector<std::string> path;
            for (size_t j = i + 1; j < cycle.size(); ++j)
                path.push_back(cycle[j]);
            for (size_t j = 1; j <= i; ++j)
                path.push_back(cycle[j]);
            return path;
        }
    }

    return cycle;
}

std::string spellString(const std::vector<std::string>& path) {    // (9)
    if (path.empty()) return "";
    std::string result = path[0];                                   // (10)
    for (size_t i = 1; i < path.size(); ++i) {
        result += path[i].back();                                   // (11)
    }
    return result;
}

std::string solve(const InputData& input) {                        // (12)
    auto graph = buildDeBruijn(input.kmers);
    auto path = eulerianPath(graph);
    return spellString(path);
}
```

## Разбор кода

**1. `buildDeBruijn` --- построение графа (идентично BA3E)**
```cpp
Graph buildDeBruijn(const std::vector<std::string>& kmers) {
    Graph graph;
```
- `using Graph = std::map<std::string, std::vector<std::string>>` --- теперь ключи и значения строковые (в BA3G были `int`).
- `const std::vector<std::string>&` --- вектор k-меров по константной ссылке (без копирования).
- Функция возвращает граф по значению --- компилятор применит NRVO (Named Return Value Optimization), фактического копирования не будет.

**2-3. Извлечение префикса и суффикса**
```cpp
std::string prefix = kmer.substr(0, kmer.size() - 1);
std::string suffix = kmer.substr(1);
```
- `substr(0, k-1)` --- первые k-1 символов: `CTTA` -> `CTT`.
- `substr(1)` --- без первого символа: `CTTA` -> `TTA`.
- Каждый вызов `substr` создаёт новую строку (аллокация в куче для строк длиннее 15 символов --- порог SSO).
- `kmer.size() - 1` безопасен: `validateInput()` гарантирует `k >= 2`.

**4. Автоматическая склейка узлов**
```cpp
graph[prefix].push_back(suffix);
```
- Если k-мер `TTAC` имеет префикс `TTA`, а ранее k-мер `CTTA` имел суффикс `TTA`, они ссылаются на **один и тот же** узел `TTA` в `map`.
- `map::operator[]` при первом обращении к ключу создаёт запись с пустым `vector<string>`. При последующих --- возвращает ссылку на существующий вектор.
- Это и есть «склейка» из теории графов де Брёйна --- реализованная одной строкой.

**5. `eulerianPath` со строковыми узлами**
```cpp
std::vector<std::string> eulerianPath(Graph& graph) {
```
- Алгоритм идентичен BA3G, но вместо `int` --- `std::string`. Все сравнения строк --- лексикографические, O(k) на сравнение.
- Параметр `Graph&` (мутабельная ссылка) --- функция временно модифицирует граф (добавляет/удаляет временное ребро).

**6. Sentinel value для строк**
```cpp
std::string startNode, endNode;
```
- В BA3G использовали `-1` как sentinel. Для строк --- пустая строка.
- Пустая строка не может быть валидным (k-1)-мером при k >= 2, поэтому это безопасный sentinel.

**7. Проверка через `empty()` вместо `== -1`**
```cpp
if (startNode.empty()) {
```
- `std::string::empty()` --- O(1), проверяет `size() == 0`.
- Семантически эквивалентно `startNode == -1` в целочисленной версии.

**8. Сравнение строк при разрезании цикла**
```cpp
if (cycle[i] == endNode && cycle[i + 1] == startNode) {
```
- `operator==` для `std::string` --- посимвольное сравнение, O(k).
- В худшем случае проверяем O(|E|) пар --- суммарно O(|E| * k).
- На практике первое несовпадение обнаруживается за O(1) в большинстве случаев.

**9. `spellString` --- восстановление строки из пути**
```cpp
std::string spellString(const std::vector<std::string>& path) {
```
- Путь --- последовательность (k-1)-меров (узлов графа де Брёйна).
- Соседние узлы перекрываются на k-2 символов: `GGC, GCT` --- общая часть `GC`.
- Поэтому от каждого узла (кроме первого) нужен только последний символ.

**10. Первый узел --- целиком**
```cpp
std::string result = path[0];
```
- Копирование первого (k-1)-мера. Для `GGC` результат начинается с `GGC`.
- `result` будет расти посимвольно --- `std::string` автоматически увеличивает буфер (амортизированное O(1) на `+=`).

**11. `back()` --- последний символ строки**
```cpp
result += path[i].back();
```
- `std::string::back()` --- O(1), возвращает `char&` на последний символ.
- `operator+=` для `char` --- добавление одного символа к строке, O(1) амортизированно.
- Для пути `GGC, GCT, CTT, TTA, TAC, ACC, CCA`: `GGC` + `T` + `T` + `A` + `C` + `C` + `A` = `GGCTTACCA`.

**12. `solve` --- композиция трёх шагов**
```cpp
std::string solve(const InputData& input) {
    auto graph = buildDeBruijn(input.kmers);
    auto path = eulerianPath(graph);
    return spellString(path);
}
```
- Три строки --- три шага конвейера. Каждый `auto` выводит конкретный тип:
  - `graph` : `Graph` = `std::map<std::string, std::vector<std::string>>`
  - `path` : `std::vector<std::string>`
  - Возвращаемое значение: `std::string`
- `buildDeBruijn` возвращает по значению (NRVO), `eulerianPath` принимает по ссылке (модифицирует), `spellString` принимает по const-ссылке (только читает).

## Анализ сложности

### Время: O(n * k * log n), где n --- число k-меров

**Обоснование.** Три фазы конвейера:

1. **buildDeBruijn:** n k-меров, каждый --- два `substr` за O(k) + вставка в `map` за O(k * log m), где m --- число уникальных узлов (m <= 2n). Итого: O(n * k * log n).

2. **eulerianPath:** O(|E| * log |V|) = O(n * log m) для Хирхольцера (из-за `map`). Сравнение строк при разрезании цикла: O(n * k). Суммарно: O(n * k).

3. **spellString:** один проход по n узлам, O(1) на узел. Итого: O(n).

**Узкое место в коде:**
```cpp
graph[prefix].push_back(suffix);       // O(k * log m) — поиск в map по строковому ключу
```
Вставка в `map<string, ...>` --- bottleneck: O(log m) сравнений строк длины k-1, каждое за O(k). Суммарно для n k-меров: **O(n * k * log n)**.

С `unordered_map` первая фаза ускорилась бы до O(n * k) (хэширование строки за O(k)), но пришлось бы сортировать ключи отдельно для вывода. Для задачи Rosalind порядок вывода не важен, так что `unordered_map` --- валидная оптимизация.

### Память: O(n * k)

**Обоснование.** Доминирует граф де Брёйна:

**Основные структуры данных:**
```cpp
Graph graph;                              // m узлов + n рёбер, каждое — строка длины k-1
std::vector<std::string> path;            // n+1 узлов, каждый — строка длины k-1
std::string result;                       // итоговая строка длины n+k-1
```
- Граф: m <= 2n уникальных узлов (строки длины k-1) + n суффиксов в векторах (строки длины k-1). Итого: O(n * k).
- Путь: n+1 строка длины k-1. Итого: O(n * k).
- Результат: одна строка длины n + k - 1. Итого: O(n + k).
- `map` overhead: ~48 байт на узел дерева (указатели left/right/parent, цвет, ключ, значение).
- Для *E. coli* (n ~ 4.6M k-меров, k = 55): ~4.6M * 54 * 3 ~ 750 Мб на строки. На практике ассемблеры используют компактные хэш-таблицы с битовым кодированием нуклеотидов (2 бита на символ вместо 8), снижая потребление до ~100 Мб.
